# Project 05 Portfolio-Scale Experiment Guide

## Goal

Run one reproducible local RTX experiment that produces a trained FLAN-T5 LoRA adapter, a held-out base-versus-adapter comparison, auditable per-example predictions, plots, and Hugging Face publication artifacts.

## Recommended execution path

1. Open `notebooks/05_end_to_end_gpu_lora_training_evaluation.ipynb` in JupyterLab or VS Code.
2. Run the project-location cell.
3. Set `INSTALL_DEPENDENCIES = True` for the first environment setup, run the cell, restart the kernel, and change it back to `False`.
4. Run the hardware cell and confirm:
   - `cuda_available: true`
   - the expected NVIDIA RTX model is displayed
   - GPU VRAM is reported
   - BF16 or FP16 is selected when supported
5. Build the extended curriculum. The generator writes:
   - `data/ml_ds_instruction_dataset_extended.jsonl`
   - `data/evaluation_prompts_extended.jsonl`
   - `outputs/extended_dataset_statistics.json`
   - `outputs/extended_dataset_validation_report.json`
6. Review the category and split charts.
7. Train the LoRA adapter. The run is saved under:
   - `models/experiments/<run-id>/adapter/`
   - `models/experiments/<run-id>/training_metadata.json`
   - `models/experiments/<run-id>/training_log_history.json`
8. Run the base-versus-LoRA evaluation. The same deterministic generation settings and the same held-out prompts are used for both models.
9. Review the aggregate scorecard, paired bootstrap intervals, per-category scores, and individual responses.
10. Open `outputs/portfolio_experiment/manual_review_results.csv`, complete the human review, and rerun the manual-summary cell.
11. Synchronize results to `web/public/evaluation-summary.json` and generate `outputs/README_RESULTS_SNIPPET.md`.
12. Upload the adapter to a Hugging Face model repository only after the run and manual review are complete.
13. Merge and export the adapter to ONNX only after the adapter has demonstrated useful held-out improvements.

## What the notebook measures

| Evaluation dimension | Output |
|---|---|
| Held-out sequence loss | `heldout_loss` |
| Perplexity | `perplexity` |
| Semantic reference similarity | BERTScore precision, recall, and F1 |
| Lexical overlap | ROUGE-1, ROUGE-2, and ROUGE-L |
| Response relevance | Sentence-Transformer similarity to prompt and reference |
| Instruction adherence | Transparent category-aware heuristic components |
| Reference support | Embedding support score against the curated reference |
| Hallucination-risk triage | Unsupported numbers, attributions, absolutes, and low support |
| Runtime behavior | Warm-cache latency, output tokens, throughput, and peak GPU memory |
| Uncertainty | Paired bootstrap confidence intervals and Wilcoxon test where valid |
| Human quality | Correctness, relevance, clarity, preference, and hallucination labels |

## Why the comparison is credible

- The base model and adapter use the same held-out records.
- Topic-group splitting keeps paraphrases of a concept in one split.
- Generation is deterministic during evaluation.
- Per-example outputs are saved, so aggregate metrics can be audited.
- Base-versus-LoRA deltas are paired by prompt.
- Numeric results are generated by execution rather than entered manually.
- Automated factuality proxies are labeled as proxies and supplemented by human review.

## RTX batch guidance

The notebook selects a conservative micro-batch automatically:

| Reported VRAM | Micro-batch | Gradient accumulation | Effective batch |
|---:|---:|---:|---:|
| 16 GB or more | 8 | 2 | 16 |
| 8–15 GB | 4 | 4 | 16 |
| Below 8 GB | 2 | 8 | 16 |

If CUDA runs out of memory, reduce `train_batch_size` before changing model architecture. Keep the effective batch size similar by increasing gradient accumulation.

## Interpreting results honestly

A stronger LoRA result should show improvement across several dimensions rather than only lower training loss. Look for:

- lower held-out loss or perplexity;
- positive paired BERTScore, ROUGE-L, relevance, and adherence deltas;
- improvements across multiple prompt categories;
- acceptable latency and memory overhead;
- fewer or no additional hallucination-risk flags;
- human-review preference for the adapter on correctness and clarity.

If the adapter improves lexical similarity but reduces factual correctness in manual review, do not present it as a successful final model. Improve the data or training configuration and rerun the experiment under a new run ID.

## Artifacts to publish

Commit small metrics, predictions, plots, documentation, and configuration to GitHub. Publish adapter weights in a Hugging Face model repository. Avoid committing large checkpoints and merged model weights to ordinary Git history.
